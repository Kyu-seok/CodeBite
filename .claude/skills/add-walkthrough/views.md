# Views for common shapes

What the Arrays & Hashing Walkthroughs settled, on top of the public skill's `references/format.md`. Each line names a tracer in `scripts/walkthroughs/` that does it. Every Walkthrough meets the two rules in the checklist (`add-walkthrough` step 3): each frame shows where its value came from and went, and a value with a place in the data is drawn there, with only the rest in `vars`.

## Shapes

- **A hash map** is a `map`, never a `table` or a list in `vars`: `{"entries": map_entries(counts)}` draws one key card per entry in insertion order, a count as dots and the number, a list as chips. Mark the key a step changed `good`. Each value read moves into its key's card: `moves=[move(at("log", i), at("uses", machine))]`. A ranking is its own frame, `ranks` badging the keys #1, #2… with the ones the answer takes `path` and the rest `dim`; then each one moves into an `output` view, which shows the answer forming (`top-espresso-machines`). A list value is chips: each word moves into its key's card as one (`group-anagrams`). A value that is an index, not a count, goes in as text (`f"i={j}"`), or it draws as dots (`snack-drawer-pair`). Two counts compared (one per string) are two maps, each letter moving into its string's (`valid-anagram`).
- **A lookup** in a map (a partner `target - x`, a running total `total - k`) is the map's `probe`, never a `vars` value: `{"key": need, "label": f"{target} − {x} = {need}", "hit": need in seen}`, looked up before the step stores its own key, so a value that is its own partner still misses. A hit rings the card; the values the answer takes then move from the map and the array into an `output` (`snack-drawer-pair`), or each window it counts moves from the hit card into an `output` of counted windows, drawn as spans on the array, so the answer is how many the box holds (`battery-window-tally`).
- **The answer** that is built up (a list of picks, a whiteboard) is an `output` view its values move into, not a `vars` list.
- **A set** is a `set`, never a `table` row or a list in `vars`: `{"members": order}` draws one chip per member in the order they went in (keep your own list beside the Python set, whose order isn't insertion order). Each lookup is a probe on that frame, `"probes": [probe(x, hit=x in seen)]`: a hit lights the member it finds, a miss is dashed. A value looked up and then added in the same step is `probe(x, hit=False)`, its member marked `good`, and it moves in from where it was read: `moves=[move(at("lockers", i), at("seen", x))]`. The repeat that ends the run marks both cells and the member `path` (`spot-duplicate-locker`). Probe exactly what the solution looks up: `any(k in seen for k in keys)` stops at the first hit, so the keys after it are not probed (`valid-sudoku`, whose three keys are three map lookups).
- **A loop over a set** draws the set in its loop order (`list(seats)`), fading the members already visited, and probes what each step asks (`probe(seat - 1, label="seat - 1")`, then each seat a walk counts up through, ending on the miss). A run of consecutive values found that way is a span on an `array` of the same values sorted, one span per run (`len 3`), with the longest a `below` span; its title ("the same seats, by number") says the solution never sorts them (`longest-seat-run`).
- **A set of composite keys** (region, value) is drawn as the solver pictures it: one `map` per key family from the region to the values seen there, never string keys like `"1:5"`. A card per region seen so far, keyed `"row 1"`, `"col 4"`, `"box 1,1"` with a `label` in each language (`{"en": "row 1", "ko": "1행"}`), its value the chips of the digits seen there. Each map gets the step's `probe` (`{"key": "row 1", "hit": ..., "label": {"en": "5 in row 1?", "ko": "1행에 5?"}}`), in the order the solution looks the keys up, and the digit moves from its cell into each card (`value=` the digit). A repeat marks the chip it hits (`"marks": {"bad": [i]}` on the entry) and both cells `bad`. The board is a grid with `"boxes": 3` and empty cells blank (`{".": {"glyph": ""}}`), and the cell read is `lit` with its row, column and box in `shade` (`valid-sudoku`).
- **Strings** longer than about 4 characters go in table cells: `array` cells are a fixed 46px. A table cell is a move's address, `[row, col]`, so a word still moves out of its row (`group-anagrams`). A string walked letter by letter is an `array` of its characters; a string that grows is an `array` padded with `""` to its final length, so cells keep their place, each written character moving in from the table cell it came from, with the length's digits from its length cell (`chat-log-codec`).
- **Intervals** sit on one number line, an `intervals` view, never two tables: the input sorted and the output so far are two `groups` over one axis (pin it with `domain` in the run `setup`, so it holds still while the output grows). Light the interval read, mark the output interval it lands in `good`, and move it there: `moves=[move(at("line", [0, i]), at("line", [1, j]))]`, an address being `[group, index]`. The boundary compared is a `points` entry on the axis (`{"at": last_end, "label": ..., "mark": "lit"}`), drawn from its value before the step, not in `vars`. The last frame marks the output group `path` (`merge-reservation-slots`).
- **A queue** (a BFS frontier) is a `queue` view, never a list in `vars`: a horizontal pipe, front on the left, with each value tagged by its BFS layer (`[i, {"en": "min 2", "ko": "2분"}]`), the same tag its cell carries on the grid, so the queue shows one wave followed by the next. A grid cell's address is `[row, col]` and a queue's is the position from the front. A value joining moves in from its cell, `move(at("tray", [r, c]), at("queue", back + i), value=f"{r},{c}")` (pass `value`: a cell carries its glyph otherwise), marked `good` in the queue. The front leaving is its own frame: it stays at position 0 marked `lit` and moves out to each cell it changes, `move(at("queue", 0), at("tray", [nr, nc]))`, or is dropped (`move(at("queue", 0))`) when it changes nothing; what it changed joins the back on the next frame. The minute is the layer tag, not a `vars` value; the last frame marks the cells of the last minute `path`, so the answer reads off their tags, and dims what is still queued when the loop stopped early (`rotting-donuts`). A deque (a sliding window's monotonic deque) is the same view with `"deque": True` in its config, open at both ends.
- **A rotation through a temp** (four cells around a ring) is one frame per assignment, each a move: `temp ← top`, `top ← left`, `left ← bottom`, `bottom ← right`, `right ← temp`. The temp is a one-cell `array` titled temp, so it is an address (`at("temp", 0)`), never `vars`; light the four cells of the group and mark the cell written `good`. A cell overwritten from another keeps both copies until the other is overwritten in turn, which is how the in-place loop really runs. Tag each pixel with its starting cell, copied with it, so the last frame shows where every pixel went (`rotate-pixel-art`).
- **A graph relaxation** (Bellman-Ford, Dijkstra) keeps the costs in arrays indexed by node, never a `table`: for a round-limited Bellman-Ford, `last` (what every edge reads) and `now` (what this round writes). A graph address is a node id or an edge `[from, to]` (either order on an undirected graph). The edge tried is one frame with two moves: last round's cost goes up onto the edge, `move(at("last", a), at("cafes", [a, b]))`, and the sum comes down into the cost it beats, `move(at("cafes", [a, b]), at("now", b), value=cost)`, marked `good` there; a sum that doesn't beat it is dropped at the edge, `move(at("cafes", [a, b]), value=cost)`. A round's start moves each reached cost up from `now` into `last`. An edge from a node not reached last round has nothing to move: light the edge and say why in the caption. The last frame marks the route's nodes and edges `path`, and in `last` the costs it used (`cheapest-courier-route`). The graph is drawn as the description's graph Diagram is: nodes on a circle in `nodes` order, the first at the top, going clockwise, so list the source first; each weight sits beside its edge, and a node's tag and value outside the circle.
- **Bit tricks** are an `array` with fixed-width binary tags; the running value is an `output` box of one chip, decimal and bits, that each value moves into (`lonely-candy`).
- **Pointers over one array** are carets, and each region they bound is a span: the kept front (`dedupe-textbook-shelf`), the settled 0s, 1s and 2s (`sort-colors`). A copy is a move between cells, `move(at("books", i), at("books", k))`; a swap is `swap(view, i, j, a, b)`, the two moves with the values before it (`sort-colors`, `missing-sock-number`). A reverse is a move per cell to its mirror place, the middle one of an odd range staying (`next-speaker-order`, whose falling tail is a span and whose pivot a `below` span while the search for its swap partner runs). `WalkthroughsMatchSamplesTest` fails on an array cell that changes with no move into it.
- **A running product or count** is a span over the cells it covers, labelled with its value, moving from the span's nearest cell into the cell it fills (`product-of-all-other-elements`); a candidate with a count is a `map` with `slots=1` that each vote moves into as `+1` or `−1`, struck when the count reaches 0 (`majority-vote`).
- **A table wider than about 7 data columns** is clipped at 390px: turn it, one row per item (a 9-wide table becomes 9 rows of k columns).
- **A window** is a span on its array, never `vars` values: `"spans": {"window": span(left, right, {"en": f"window {length}", "ko": f"구간 {length}"}, fade=True)}` draws a bracket above the cells labelled with its length and fades the cells outside it; the `left`/`right` pointers stay as carets, and cells not read yet are `unread` (dashed). The best so far is a second span, `span(a, b, {"en": f"best = {best}", "ko": f"best (최장 길이) = {best}"}, below=True)`, dashed under the cells, marked `good` on the frame that beats it. The counts in the window are a `map` with `slots=k` when the window holds at most k keys, so the key that overflows shows red; that frame marks the window span `bad`. Each element dropped from the left is its own frame: it moves out of the map back to its cell (`move(at("window", g), at("queue", i), mark="bad")`), and a key whose count reaches 0 stays with value 0 and in `struck` for that frame. The last frame hides the window span and the pointers, marks the best span and its cells `path`, and the caption says where the run actually ended when the best window came earlier (`longest-window-with-at-most-k-genres`; the public skill's `examples/window-at-most-k-distinct`).
- **A running value** with a place (a prefix sum, a window length per right end) goes `under` its cell: `"under": [[i, str(total)]]`; a count of each running value is a `map` the reading moves into (`battery-window-tally`).

## Trees, linked lists and recursion

The kit's `tree`, `linkedlist` and `callstack` views (the public skill's `references/format.md`), and how CodeBite draws recursion. Walkthroughs that use them: `tree` in `binary-tree-level-order`, `valid-score-bst`, `kth-highest-raid-score`, `running-median-timer` (heaps), `username-trie`, `wildcard-lexicon` (tries) and `power-set` (a recursion tree); `linkedlist` in `reverse-linked-list`, `detect-portal-loop`, `merge-leaderboard-runs`, `drop-nth-reservation`, `interleave-clip-chain`, `add-score-lists`, `merge-cafe-queues`, `lru-cache`, `flip-chunks-of-k`, `swap-print-pairs` and `clone-quest-log`; `callstack` in `n-queens`. The kit's examples (`~/Work/walkthrough-skill/examples/tree-*`, `linkedlist-*`, `callstack-n-queens`) show more.

- **A binary tree** given as a Level-Order Array is a `tree` with `"arity": 2`: `level_order_tree(values)` gives `nodes` and `edges` with each node's array index as its id and a gap where a child is `null`. Put it in the run `setup`; each frame carries `nodeMarks`, `edgeMarks` (`[from, to]`), `tags` and `shade`. A tree drawn in the description's Diagram keeps the Diagram's look: values in the nodes, left before right.
- **A heap** is a `tree` from its array, each node tagged with its index (`[i, f"[{i}]"]`); a sift is a swap between two node ids, `swap("heap", i, j, a, b)`, the same as in its array. Two heaps (a running median) are two `tree` views.
- **A trie** is a `tree` grown with `Tree()`: each letter is the `label` on the edge into its node, the node's value empty, and a word's end `"✓"` (`t.set(id, "✓")`). Each letter inserted is a move from the word into its new node (a new node arrives with the edge into it, so the one move draws both); a search walks the nodes `lit`, the path so far `shade`.
- **A linked list** is a `linkedlist`: build its state each frame with `linked_list(order)`, `order` every node in input order, kept for the run, so a reversal turns arrows and never moves a node. Pointers are `node_id(order, p)` above their node; a pointer at null is hidden, so the caption says it is null. The step that re-points an arrow marks it `good` in `linkMarks` and draws the arrow it replaced in `cut`; a loop back is drawn under the row. One assignment per frame: saving `next`, turning the arrow and stepping the pointers are the frames the solution's lines are.
- **A dummy node** is the first node of the row, drawn empty (`ListNode("")`: its value is never read) with a `dummy` pointer over it for the whole run; the answer frame dims it and moves each node from `dummy.next` on into an `output` (`swap-print-pairs`, `drop-nth-reservation`, `flip-chunks-of-k`). Show only the pointers the current step uses; a chunk's reversal starts `prev` at the node after the chunk, so the turned arrows already lead out of it (`flip-chunks-of-k`).
- **Lists merged by relinking** stay one row, each input's nodes after the last's behind the dummy, so the merged order shows as arrows weaving over and under the row; `tail.next = x` re-points tail's arrow (the old one in `cut`) and moving tail is its own frame (`merge-leaderboard-runs`). With a heap of fronts, the heap is a `tree` tagged with each entry's list (`q1`), heapq written out as textbook sifts as `running-median-timer` does; a front joins with a move from its node, and a pop moves from the root to its node (`merge-cafe-queues`).
- **A list the solution builds** (a sum written digit by digit) is a `linkedlist` of its own that grows to the right, each new node moved into from the input nodes it was made from; a carry with no place is `vars` (`add-score-lists`).
- **A doubly linked list** draws `next` above the row and `prev` under it as the view's second link (`links: {"prev": ...}`), the nodes in the order they were made with stable ids (a key, `"head"`, `"tail"`), not `linked_list`'s indexes, which shift when a node leaves. Frames fall between whole list operations (unlink, append, evict); each marks every arrow it re-points, `next` by node id and `prev` as `["prev", id]` in `linkMarks`, and draws the ones replaced in `cut` and `linkCuts`. A node unlinked keeps its own stale arrows until it is appended, as in the code. Name both links in the view's title (`next above, prev below`). A node's value changing moves into it, like its map card (`lru-cache`).
- **A second pointer per node** (a copy's `random`/`related`) is the `linkedlist` view's second link: `linked_list(order, link="related")`, drawn under the row; never fold it into `pointers` or a table. A deep copy is a second `linkedlist` of the copies, each at its original's position so `copies[node]` is the node at the same position: each copy made is a move from its original, and its links are drawn once the solution sets them, one assignment per frame, the original's arrow `lit` and the copy's `good` (`clone-quest-log`).
- **A call stack** is a `callstack`, one `call(name, **args)` per open call, bottom first. A call pushed is a move into its card; a call returning stays drawn the step it leaves (marked `bad` for a dead end, `dim` when it returns normally) and is gone the next frame. Whatever it changed on the data and undoes leaves with a move out marked `bad` or dropped.

**Recursion** is drawn one of three ways (#359):

- **A recursion tree** (`tree`, grown one call per frame with `Tree()`) when every sample's whole call tree fits, about 15 calls or fewer, and each call means something on its own: `power-set` makes 8 calls on `[2,5,8]`, one per subset. The edge into a call carries its choice (`"+5"`, `"take 5"`), the calls still open are `shade`, the current one `lit`, and each call's result moves into the `output`. A wide tree turns on its side to fit a phone's card, the root at the left.
- **A call stack plus the current path** (`callstack` beside the data) when the call tree doesn't fit: `n-queens` draws the board with the queens placed so far and the attacked squares in `shade`, and the call stack beside it.
- **No drawing of its own** when the recursion walks a data tree (`valid-score-bst`): the input `tree` is the drawing, the current call's node `lit`, the nodes still on the stack `shade`, and each visited node tagged with what its call carries (its bounds `(30, 70)`, a depth, a count).

### Trees (#370)

- **A value returned up the tree** (a depth, a height, a gain) is a node tag set the frame its call returns, `good` on that node, with a move from each child into it carrying the child's value (`value=str(depth)`). A node with children gets a frame when its call starts (`lit`, asking its first child) and one when it returns; a leaf gets only the return frame. A running record beside it (the best path so far) is an `output` of one chip that each new record moves into from its node, `-∞` before the first; the last frame marks the record's path, nodes and edges, `path` (`deepest-skill-chain`, `longest-folder-path`, `best-skill-tree-path`).
- **A tree built from another** (a mirror) is a second `tree` beside the input, grown with `Tree()` using the input node's id (`add(value, parent=..., slot=..., id=node.id)`), each node moving across from its input node; the two side by side match a Diagram with `after:` (`mirror-menu-tree`). A tree built from arrays grows the same way, each value moving in from its array cell, with the call's range a faded span over the array and its two halves `below` spans (`rebuild-tree-from-traversals`).
- **Two trees compared in step** are two `tree` views, the pair compared `lit` in both and the open pairs `shade`; a missing child is shown on its parent, `bad`, with the caption naming the side (`same-skill-trees`).
- **A walk written out as tokens** (a preorder serialization with `#` for a missing child) is an `array` padded with `""` to its full length (2n + 1), each token moving in from its node, a `#` from the parent missing the child; an `output` draws only `good` and `dim` on its chips, not `lit`, `bad` or `path`. The search over it is a span: the match `path`, or the closest stretch `bad` with the first token that differs (`find-submap`).
- **An explicit in-order stack** is a `stack` view beside the tree: each push moves in from its node, each pop leaves to its node, which takes a tag with its place in the order (`1st`, `2nd`) (`nth-lowest-score`). A walk down a BST is the node compared `lit`, the way down `shade`, and the targets tagged `p`/`q` (`lca-bst`). A level list rebuilt each round is an `array` whose cells move in from their nodes (`right-side-skill-view`).
- **A value carried down the tree** (the max above a node, the sum or number so far) is a node tag set on the call's frame, with a move from the parent carrying it (`value=f"+{node.val}"`); when the call also returns something, the tag grows to both, `max 4 → 2` (`count-top-heroes`, `list-skill-build-paths`, `sum-root-to-leaf`). A leaf adding to a total moves into an `output` of one chip as `+25`; a path copied out moves from its leaf into an `output` as one chip, `[10,6,3]`. A failure passed up (a `-1` height, no target found) is a tag too, `✗` or `→ none`, `bad` where it starts (`balanced-hamster-tree`, `lca-binary-tree`).
- **A level written in another order** (zigzag) keeps the level `array` left to right, as the children come, and tags each cell with its place in the row it is written into (`[1]`, `[0]`); the row moves into the `output` as one chip (`zigzag-yearbook-order`).
- **A codec** is the input `tree`, a `queue`, the tokens as an `array` padded to 2n + 1 and the rebuilt `tree` grown with `Tree()` (ids the token indexes): serialize is one frame per token (the front leaving into it, its children joining the back, `#` from the parent), deserialize one per node taken, its two children moving from their tokens into the new tree and on into the queue (`binary-tree-codec`).
- **A tree rewired in place** (flattening) is drawn as it stands after each step, built each frame from the live nodes; a node that changes parent makes the view lay out each frame on its own, so the tree reshapes. A tree can't draw a node with two parents, so pointer writes that pass through one (`tail.right = node.right` before `node.right = node.left`) are one frame, the moved subtrees each moving in from the node they left; say so in the docstring. `node` and `tail` are tags (`flatten-agenda-tree`).
- **A link between nodes on one level** (`populating-next-pointers`' `next`) is the `tree` view's second link: `links`, `{"next": {id: id or None}}`, built with `tree_links([nodes...], "next")` from the solution's nodes (each carries its view id), drawn dashed pill to pill along the level, `null` to `∅`. Show only the links the walk has set, plus a level's last node's `null` once the caption says it stays null; the link a step set is `good` in `linkMarks` (`["next", id]`), the one it follows `lit`, with the walking pointer a node tag moved along by a move between the two nodes (`value="node"`). The answer read along `next` moves each value from its node into the `output`, and each `#` from the level's last node.
- `tree_values(root)` in `codebite.py` turns a built tree back into the Level-Order Array the Driver prints.

### Tries and Backtracking (#371, #373)

- **A trie walked with a grid DFS** draws no call stack: the board and the trie are the drawing, the current cell and node `lit`, the open calls `shade` on both. A cell the code marks `"#"` keeps its letter, shaded, so the word stays readable; the caption says it is marked. Each word sits on its end node as the node's value and moves into the `output` when found; a node pruned is marked `bad` with a drop move and is gone the next frame (filter it out of `Tree().state()`). Consecutive returns are one frame naming the calls (`word-search-ii`). A single-word search tags each cell on the trace with the index it matched (`i=2`) and draws the word as an `array` with `i` on the letter the call matched (`word-search`).
- **A recursion tree over a list** (subsets, sums, orders) puts the call's partial answer in the node, a value the call carries (what is left to spend) as a node tag, and on the input array fades the cells before `start`, lights the ones the call will try and marks `bad` the ones too dear. A call that makes no call is `bad` until the last frame dims it (`voucher-price-combos`, `menu-combos-tab`, `cafe-stop-orders`). A choice skipped because it equals the one just tried gets a frame of its own, the skipped cells `bad`: it is what keeps the answers distinct (`snack-combo-picks`, `menu-combos-tab`). Choices rejected by a check (a piece that is not a palindrome) are named in the next call's caption, or in a frame where the call gives up when no call follows (`palindrome-menu-splits`).
- **A call stack over a string** (segments, pieces) draws each piece taken as a span over its characters, labelled with the piece, the card's note the answer so far (`19.216`); the calls returning together leave in one frame, their spans' cells `bad`, and the caption names the lengths the deepest of them passed over (`restore-wifi-ip`).

## Marks, tags and ids

- `lit` wins over `good` on the same item: mark a changed cell `good` only.
- A `vars` item's `mark` colours a number; the chips of a list value ignore it.
- For an index-slot or cyclic-placement problem, tag each cell with what it stands for (`for 3` / `3번 칸`), and draw each placement as a move between cells: a swap into place is two (`missing-sock-number`), and a slot marked for the value read is a move from the cell read into the slot, or a move with no `from` when a cell marks its own slot (`repeat-attendance-codes`). For a running count, tag each read cell with its effect (`+1`, `−1`). Tags take Text (`missing-sock-number`, `majority-vote`).
- A view id `answer` or `moves` collides with `run.frame(answer=..., moves=...)` (a TypeError): name it `result`, titled "answer".
- View titles are uppercased by the kit's CSS; a table with no `columns` draws no header row.

## Two Pointers, Sliding Window, Stack, Binary Search, Graphs (#361 A1)

- **A running max** (trapping water's level on each side) is a tag on the bar that set it (`L max 3`), moved when a taller bar takes over, never `vars`; the water total is an `output` of one chip each bar's water moves into (`trapping-rain-water`).
- **A read and a write pointer** in the same direction keep the In-Place Method's two regions as spans: the kept front above, and the slots a second loop overwrites as a `below` span with that loop's own pointer; a slot written with a constant is a move with no `from` (`move-voided-scans`).
- **A fixed-size window compared with a target count** is two `map`s, the target's and the window's; after each slide the keys whose counts differ are `bad` on both, so the frame shows why it isn't a match yet. The add and the drop are separate frames, the window span `bad` while it is one too long (`find-name-anagram`).
- **A count that goes negative** (minimum cover's `missing`, spare copies) stays in its `map`: a negative number draws as text. A total kept beside it (`to_cover`) is `vars` with a `why`, since it can equal a card by chance (`shortest-book-span`).
- **A running minimum** paired with each later value (best buy-then-sell) is a pointer `low` on its cell, the pair compared a window span from `low` to `j` labelled with the difference, each value's difference `under` its cell and the best pair a `below` span: no `vars` at all (`peak-temp-jump`).
- **A last-seen index per key** (the window's start jumping past a repeat) is a `map` whose values are text (`"i=3"`), a card whose index is before the window's start `dim`; each key read is the map's probe, asking "in window?" (a stale card misses). A repeat inside the window is its own frame, both copies `bad`, before the frame where start jumps and the card takes the new index (`longest-genre-window`).
- **A running sum** compared with a target is an `output` of one chip, titled for the window, that each value added moves into as `+c` and each value dropped as `−c` (marked `bad`), so the chip never changes without a move; the target is `vars` (`shortest-cookie-span`).
- **A monotonic deque** is a `queue` with `"deque": True`, each entry its value tagged with its index (`beat 2`): a pop from the back stays drawn `lit` and is dropped, a push moves in from its cell, the front leaving is dropped from position 0, and each window's answer moves from the front into an `output`. When no sample's front slides out of the window, add an extra run where it does (`peak-combo-window`).
- **A stack** is a `stack` view, drawn upright on a fixed base with the top at the top (#383), never an `array` with its top on the right. Build its state from the solution's own list with `stack(items, value=..., tag=...)` and add `marks`: a push moves in from where the value was read, `move(at("readings", day), at("pending", len(pending) - 1))`; a pop stays drawn, `lit`, for the frame it leaves and moves out to where its value goes, and is gone the next frame. Tag each entry with what it stands for when the value isn't the key (`day 2` over a reading: `days-until-warmer`, whose monotonic pops leave from the top one frame each). An operator is two frames: the two operands `lit` and tagged `a`/`b`, then the result moving from the operator's token into `a`'s place (`eval-postfix-tape`). Two stacks are two `stack` views next to each other in `views`, so they stand side by side, at 390 too (`queue-from-stacks`).
- **Binary search over indices** is the range as a faded span with `low`/`mid`/`high` pointers, and the half that is sorted a `below` span (`good` when target is in it); each frame shows the range the probe split, and the next one the range kept (`search-rotated-catalog`).
- **Binary search over the answer** draws the answer's range as one interval on an `intervals` number line (`domain` pinned in `setup`) with the rate tried as a `points` entry; one frame tries it (each item's cost `under` its cell, moving into an `output` total), the next moves the total into the interval it cuts (`slowest-snack-rate`).
- **A topological order by in-degree** keeps the graph as the description's Diagram draws it (edges as the input lists them, nodes in the order the edges name them), the in-degrees as node values: each count or decrement is a move from the edge into its node, ready tasks a `queue`, finished ones an `output` and a `#k` node tag. A cycle's last frame marks the stuck nodes and their edges `bad` (`verify-task-order`).

## Greedy, DP, Intervals and 2D DP (#361 A2)

- **A reach** (the farthest index reachable so far) is a span from 0 to it, labelled with its value, fading the cells past it; each cell read writes its own reach `under` it, and a reach that grows moves from the cell to the cell it lands on (`finish-the-level`). A run cut at a known end is a span above to the end so far, each finished run a `below` span labelled with its length that moves into an `output` (`split-sticker-runs`).
- **Rolling DP values** (two numbers carried from step to step) are a small `array` tagged with their names (`skip`, `take`), rewritten each step with a move into each cell from what it was built from; a tuple assignment is one frame with the moves carrying the old values (`pick-snack-haul`). Keep beside them what each value picked, so the last frame can mark the answer's items `path`.
- **A 1D DP table** is an `array` over its index (amounts 0..quota), unfilled cells `unread` and unreachable ones `"∞"`; each cell read is tagged with the choice that reads it (`bag 4`), and the winner moves in as `v+1`. Keep the winning choice per cell, and the last frame marks the chain of cells back to 0 (`fewest-candy-bags`). 16 cells still read at 390.
- **Intervals placed into resources** (tables, rooms) are one `intervals` group per resource under the sorted input, so a heap of end times is each group's last end, drawn on the data; the sweep's current start is the one `points` line (a second point near it collides with its label), and the resource that frees first is marked on its last interval, `lit` when free and `bad` when not (`peak-table-demand`). An interval that grows by merging is a group of its own between the input and the output, as the description's `added` row (`slot-a-meeting`).
- **Greedy (#375).** A running best that ends here (Kadane) is the streak as a span above labelled with its sum, that sum `under` each cell, a streak that goes on moving from the cell before, and the best a `below` span (`peak-score-streak`). Jump counts by layer are one `below` span per jump (`start`, `jump 1`…) under a finish-the-level reach, so the answer is how many there are (`fewest-tile-jumps`). A running total that resets is an `array` filled cell by cell, each moving in from the inputs it adds and the cell before, with the attempt a span and a `start` pointer; when no sample resets, add an extra run that does (`pick-charging-start`). A range of possible counts (open brackets) is an `intervals` row per character with a `points` line at the floor, a clamp its own frame (`balance-brackets-with-wildcards`). A count spent into groups leaves its card as a dropped `−n` and moves into an `output` chip that grows (`[1` to `[1,2]`); a card at 0 stays drawn, dimmed, as a Counter keeps it (`group-study-cards`). Pairs (`[h,k]`) are written `h,k` in one cell, not a height tagged with k: the test checks an insert by value, and equal heights look like one value shifting; an insert into a list moves the new value in and each value behind it one place back (`rebuild-tournament-line`). Triples are `table` rows (`combine-bags-to-match-target`).
- **Dynamic Programming (#376).** Rolling values over a sequence (`previous`/`current`, `before`/`current`) can be the whole table over its index with the two kept cells tagged and the ones behind them dimmed, each new cell moving in from the cells it adds; a part that isn't allowed is a span `bad` and adds no move, a cell built from nothing is a created `0` (`count-level-hops`, `count-cipher-decodings`). Two passes over overlapping ranges (a circle cut two ways) are a fading span per pass above the input, with the rolling cells restarting through created moves; a finished pass's best is a `below` span, one at a time because overlapping spans share a row (`pick-circular-donuts`). Largest and smallest products ending here are a `high`/`low`/`best` array, with the slices behind high and low as spans above and below the input (`max-product-slice`). A table read by words is tagged at each start cell with the word, the word a span over its letters, `good` above or `bad` below so two spans over one stretch don't collide (`word-break-chat`, with an extra run for a failing read). `tails` for a rising subsequence is an `array` tagged with each length, each score moving into the slot bisect finds, and the last frame marks a real run found from what each score extended (`longest-rising-quiz-scores`). Expanding around centres is `left`/`right` pointers with the palindrome so far a span; each match moves into an `output` when they're counted (`count-doodle-palindromes`) or the longest is a `below` span (`longest-palindromic-substring`). Korean tags are short words or the code name (`이전`, `현재`, `high`): a glossed tag over adjacent cells overlaps.
- **A 2D DP table** is a `grid` (an SVG, which scales at 390), not a `table` (clipped past about 7 columns). For a two-string table, the first row and column are header cells holding the letters (a `values` tone, `∅` for the empty prefix), lit with the cell they compare; unfilled cells are `" "` with an empty tone. Each cell's value moves in from the neighbour it came from, and the last frame marks the walk back (`min-cheat-code-edits`). A grid DP reads the same without headers (`count-dungeon-paths`).
- **Dynamic Programming, part 2 (#376).** Rolling values over positions that run one past the input (climbing past the last step) get an extra cell on the input array, tagged `end`, so pointer `i` has a place there; each way in writes its sum `under` the cost it pays (`min-stamina-checkpoints`). A set of reachable sums is a `set` in insertion order, each new sum moving in from the sum it was built on (`3+2`); the last frame probes the target (`split-tickets-into-equal-sums`). Merging sequences by several pointers (ugly numbers) draws the pointers as carets on the output array and the candidates as a small array tagged by factor: one frame refreshes the candidates whose pointer moved, the next moves the smallest into the output and steps every pointer that made it (`nth-unlockable-level`). An O(n²) table whose inner loop reads every earlier cell is one frame per cell, each read's candidate `under` the cell it reads (`2×3`), and the docstring says the reads are grouped (`split-candy-bar-for-max-product`); two tables filled pair by pair get a frame only per pair that passes the guard, the pairs failing it `dim` on the input (`count-longest-increasing-subsequences`). A formula over a tree (n! over subtree sizes) keeps the tree in `setup` beside the arrays the code fills, and its few scalars as one small array tagged with their names, each moving in from the cell it multiplies (`count-task-orderings`).

## A list of calls (Design; #359)

A problem driven by a list of calls (`["QueueFromStacks","push","pop",…]` and their arguments, the Driver printing what each returned) is drawn as the calls running against the structure (`queue-from-stacks`, `chat-ring-buffer`):

- **One run per sample**, its `input` the sample's two lines verbatim; one frame per call, plus one per step inside a call that changes the structure on its own (each value `_shift` moves from inbox to outbox), and a last frame that marks the output `path` and carries the answer.
- **The calls are a `table`**, one row per call in order, the constructor first, with columns call and argument (the argument blank for none): an `array`'s 46px cells clip `insert cat` or `push(1)` at 390. The current call's row is `lit`, in place of a pointer; the rows before it are `dim`, and the last frame drops the marks. A value a call adds to the structure moves from its argument cell, `at("calls", [i, 1])`; a return value the call makes itself from its call cell, `[i, 0]` (`username-trie`, `wildcard-lexicon` too).
- **Each call's return value moves into an `output`** titled "returned", one chip per call as the Driver prints it, each a string (`"null"`: the output draws a real null as an empty chip; `"true"`, `"-1"`, a number), so the box fills to the printed list. A value read from the structure moves from its place (`move(at("outbox", top), at("result", k))`); one the call makes itself (`null`, a boolean, `-1` from an empty queue) moves from the call cell, `value=` the printed text. Only the chip added this frame is `good`. The constructor's `null` is in the setup frame, which needs no move.
- **The structure changes underneath** in its own views: a stack is a `stack` view, as the A1 section above draws one, and two stacks (inbox and outbox) stand side by side; a fixed array (a ring's slots) keeps every slot, its pointers (`head`, `rear`) on it and the slots outside the structure `dim`, a value a pull leaves behind staying in its slot until a push writes over it. A field with no place in the drawing (`size`) is `vars`.
- **A call that is refused** (`push` on a full ring) changes nothing: the places it would touch are `bad` and only its return value moves.

## Heap / Priority Queue (#372)

- **A heappop is one frame** when one swap per frame would run long: the root leaves (moving to where its value goes) and the last node fills the root at once, drawn with the last node still at its index (`heap + [last]`) so the move has a place to start from; the sift-down swaps that follow stay one per frame, and the caption says the pop is one step (`crush-heaviest-blocks`, `task-cooldown-planner`, `micro-feed`).
- **A size-k heap of the best so far** (k highest, k nearest) draws what it orders by as the node value and what it stands for in the tag (`[0] (5,5)`); a candidate that beats the root replaces it, the old root moving back out `bad` to the row it came from, and one that doesn't is dropped at its cell (`kth-top-score-stream`, `nearest-cafe-stops`).
- **A cooldown** (a label that can't be picked again for n steps) is a `queue` beside the heap, each entry tagged with the step it is ready again; the front rejoins the heap with a move, and each step's pick, or an idle step, is a chip in an `output` schedule (`task-cooldown-planner`).
- **Merging per-key lists newest first** (a feed) is a heap of each list's next entry: the pop moves into the `output` being built and the same list's next older entry moves into the heap from its `map` card (`micro-feed`).

## Bit Manipulation and Math & Geometry (#379, #380)

- **A 32-bit word** (a mask, a word reversed) is a `grid` of bits, one row per byte, the highest byte first, so each row reads as binary is written; each cell is tagged with its bit number, and `values` tones the 1s. Draw as many bytes as the run needs, all 4 when the problem is about all 32 bits: a 31-cell `array` shrinks past reading at 390. A bit's mirror (31 − i) is the cell at the same place read from the other end (`online-friend-mask`, `reverse-savefile-flags`).
- **Counting 1 bits** is `x &= x − 1`, one frame per bit cleared: the cleared bit moves into an `output` count as `+1` and gets a `0` written in with no `from`, and the caption says why only that bit clears (`online-friend-mask`, `compare-loadout-bits`). `n & (n − 1)` as a test draws n, n − 1 and the result as three bit arrays, each appearing with a move per column from the one above it (`power-of-two-tank`).
- **XOR against the full range** (the missing number) draws the range 0..n as an array of its own beside the list, so each number XORed in moves from a cell; a number met in both fades in both, as `lonely-candy`'s pairs do (`find-empty-locker`).
- **Repeated squaring** draws the exponent's bits lowest first with pointer `k`, and under them an array of the squares (cell k is base^(2^k), tagged `b¹`, `b²`, `b⁴`), so a bit and its power share a column; a 1 bit moves its square into a one-chip `output` result as `×v`, and each squaring moves cell k into k + 1. A fraction reads as `1/16` in a 46px cell where `0.0625` doesn't fit (`fast-exponentiation`).
- **A number rewritten from its digits** (a digit-square chain) is a one-cell `array`, so it is an address: it splits into a digits `array` with each square `under` its digit, the squares move back into it as `+16`, and a `set` of the numbers seen takes each one as a probe before it goes in (`calm-number`).
- **A +1 carried leftward** moves from the digit that passed it on into the next, `+1`, the first one created; a new leading digit moves in from the old first digit, which is now index 1 (`bump-takeout-number`, whose extra run carries through every digit). A per-element rule (fizz-buzz, Roman numerals) is one frame per element, its tag the test it passed (`÷3,5`, the symbol's value) and its result moving into an `output`; the signed amount a symbol added stays `under` it (`fizz-buzz`, `decode-roman-floor`).
- **Two passes over a grid with sets** (rows and columns to wipe) scan a row per frame into two `set`s, then one frame per cell probing exactly what `r in rows or c in cols` looks up, the 0 moving from the member that hit (`zero-out-rows-cols`). A final caption whose answer is one long unbroken list (fizz-buzz's 15 strings) runs out of the caption at 390: point at the `output` instead of printing it.

## Graphs (#374)

- **A flood fill with a stack** (count the islands) draws the grid as its Diagram does, each seen cell tagged with its region's number (`#2`), the regions already finished `dim`; the stack is a `stack` view of `"r,c"` values. A pop stays drawn `lit` and moves out to each cell it adds (or is dropped), the cells added join the stack on the next frame, and each region started moves from its first cell into an `output` of one chip per region, so the answer is how many chips it holds (`count-desk-clusters`). Keep `shade` off a grid whose cells carry glyphs: the band darkens them past reading.
- **Two searches over one grid** (cells reaching each of two borders) tag each cell with a symbol per search (`↖`, `↘`, both `↖↘`), so the cells carrying both are the answer, which then move into an `output`. A run of pops that adds nothing is one frame, every one of them `lit` and dropped; draw the pop that does add something still on the stack in that frame, or its place changes with no move (`dual-waterbowl-flow`).
- **A graph copied node by node** is the original as its Diagram draws it beside a directed `graph` of the copy that holds every node from the first frame (a graph lays out its current nodes, so one that grows reshuffles), the copies not made yet `dim`. A copy made moves in from its original; each neighbor appended is one arrow, moving from the original's edge into the neighbor's copy, so an undirected edge ends as two arrows (`snapshot-town-map`).
- **Union-find with a count** (parties, components) keeps one `output` chip per element, its root number, and fades a chip (`dim`) at the union that ends it as a root, moving out `bad` that frame; the answer is the chips still bright. Removing the chip instead shifts the ones after it, which the move rule reads as values changing with no move (`count-voice-parties`). Union-find over strings (emails) draws them as the Diagram's graph, each node's value its parent's name and its tag the owner, with the Diagram's short names as node `label`s; then each element moves into its root's card in a `map` of groups (`merge-duplicate-contacts`).
- **An early return before the search** (an edge count against n − 1) is one frame on the whole graph, every edge `bad`; when no sample reaches the search's own failure (a cycle found by two ends sharing a root), add an extra run that does (`graph-valid-tree`). A judge that prints `VALID` for any right answer still gets its own last frame: the caption names the order returned and why the judge accepts it, and the answer is `VALID` (`order-group-tasks`, whose extra run returns `[]` on a cycle).
- **A BFS that writes distances into the grid** (rooms filled with their distance to the nearest gate) is `rotting-donuts`' queue, each front leaving moving into the cells it fills with the new distance as the move's `value`; a run of fronts that fill nothing is one frame, all `lit` and dropped (`walls-and-gates`). When the count lives in a second array (`tiles`), tag each cell with it instead of drawing a second grid, and keep a parent per cell so the last frame marks one shortest path as the Diagram highlights it (`shortest-dungeon-path`, 8 neighbours).
- **A flood that rewrites cells as it pushes** (border `'O'` to `'S'`) is drawn with the values the code writes, each write a move with no `from` (`value="S"`) or from the stack entry that reached it; the final sweep is two frames, the captures (`bad`) and the restores. The reference was rewritten to mark on push and push only in-bounds cells, so every push is a drawn cell (`capture-enclosed-tiles`).
- **A BFS over generated neighbours** (word ladder's 26 × L one-letter changes) draws the implied graph as the Diagram does, the `unvisited` set beside it: each pop's hits are the set's probes and move from the queue front into their nodes as the new length; the misses are only counted in the caption (`word-ladder`).
- **A DFS over a key or conflict graph** keeps the graph as the Diagram draws it with a `set` or node values for what is visited; a value found along an edge moves out of that edge into the node or set member (`open-all-rooms`, `two-shift-baristas`, whose shift is the node value and whose clash marks the edge and both ends `bad`).
- **One search per query** (`cafe-price-ratios`) keeps the queries a one-column `table`, the row answered `lit` and earlier rows `dim`; each query's start clears the last search's node values with `bad` drops and moves `1` in from its row, the products move along the edge walked (`×` with the arrow, `÷` against it), and each answer moves from the goal node (or from the row, for `-1`) into an `output`.

## Intervals and 2D DP (#377, #378)

- **Intervals sorted into outcomes** (kept and dropped, or one group per pellet that feeds them) are groups under the sorted input, each interval moving into its group, so the answer is a group's size or the number of groups; the boundary compared (`last end`, `last pellet`) is the one `points` line, labelled without its number, which the axis shows (`drop-conflicting-classes`, `cover-aquarium-zones`). An unsorted input is its own group above the sorted one, every interval moving down in the sort frame (`can-attend-bookings`).
- **A heap of intervals** is a group in push order: its top (the shortest) is lit, and a popped interval stays in its row, faded, since an intervals view compares rows in place and a row that shifts needs a move. A sweep over sorted queries draws the queries and the answers as two arrays, `now` on the query, the answer moving in from the heap's top (`shortest-table-booking`).
- **State-machine DP** (hold, sold, rest per day) is a `grid`, a row per state and a column per day after a `start` column, the day's price as a header cell. A tuple assignment is one frame with a move into each state; the last frame walks the choices back to the trades (`skin-resale-with-cooldown`).
- **A counter rebuilt per item** (counts per net total) is a `grid`, a row per item and a column per total any row reaches. A total spreads its count into two cells of the next row, one frame per total (`ticket-plus-or-minus`). Header numbers that could collide with cell numbers in the `values` map get a key of their own with a `glyph` (`t4` drawn as `4`); a word header (`hold`, `+3`) needs none.
- **An interval DP** (`best[left][right]`, filled by gap width) is a `grid` of left by right, headed by the padded values, cells below the base diagonal blank. The winning split's two smaller cells both move in, and the last frame walks the splits back to an order (`max-balloon-pop-points`).
- **A memoised recursion over two indexes** is a recursion tree (each call holding the rest of both strings, the edge its choice) beside the memo as a `grid`, each call's ✓/✗ moving into its cell as it returns (`match-dot-star-pattern`).
- **A boolean 2D table** draws ✓ and ✗ as glyphs; a ✗ also moves in, from the cell read, marked `bad` (`check-interleaved-inputs`).
- **A 2D DP over an input grid** draws the input as its description's Diagram (a grid of its own) beside the table of the same shape, each cell taking its own input value as a second move (`+2`) (`min-wait-drive`, `biggest-clear-floor`). A best so far is a `best` tag on its table cell; a visiting order other than row order is a `#n` tag on each visited input cell (`longest-level-up-path`). Every row-major table here stays under about 50 frames, one per cell; the 7 × 7 LCS (`desk-notes-overlap`) is the largest at 51.
