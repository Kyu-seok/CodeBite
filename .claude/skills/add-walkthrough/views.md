# Views for common shapes

What the Arrays & Hashing Walkthroughs settled, on top of the public skill's `references/format.md`. Each line names a tracer in `scripts/walkthroughs/` that does it. Every Walkthrough meets the two rules in the checklist (`add-walkthrough` step 3): each frame shows where its value came from and went, and a value with a place in the data is drawn there, with only the rest in `vars`.

## Shapes

- **A hash map** is a `map`, never a `table` or a list in `vars`: `{"entries": map_entries(counts)}` draws one key card per entry in insertion order, a count as dots and the number, a list as chips. Mark the key a step changed `good`. Each value read moves into its key's card: `moves=[move(at("log", i), at("uses", machine))]`. A ranking is its own frame, `ranks` badging the keys #1, #2… with the ones the answer takes `path` and the rest `dim`; then each one moves into an `output` view, which shows the answer forming (`top-espresso-machines`). A list value is chips: each word moves into its key's card as one (`group-anagrams`). A value that is an index, not a count, goes in as text (`f"i={j}"`), or it draws as dots (`snack-drawer-pair`). Two counts compared (one per string) are two maps, each letter moving into its string's (`valid-anagram`).
- **A lookup** in a map (a partner `target - x`, a running total `total - k`) is the map's `probe`, never a `vars` value: `{"key": need, "label": f"{target} − {x} = {need}", "hit": need in seen}`, looked up before the step stores its own key, so a value that is its own partner still misses. A hit rings the card; the values the answer takes then move from the map and the array into an `output` (`snack-drawer-pair`), or each window it counts moves from the hit card into an `output` of counted windows, drawn as spans on the array, so the answer is how many the box holds (`battery-window-tally`).
- **The answer** that is built up (a list of picks, a whiteboard) is an `output` view its values move into, not a `vars` list.
- **A set** is a `set`, never a `table` row or a list in `vars`: `{"members": order}` draws one chip per member in the order they went in (keep your own list beside the Python set, whose order isn't insertion order). Each lookup is a probe on that frame, `"probes": [probe(x, hit=x in seen)]`: a hit lights the member it finds, a miss is dashed. A value looked up and then added in the same step is `probe(x, hit=False)`, its member marked `good`, and it moves in from where it was read: `moves=[move(at("lockers", i), at("seen", x))]`. The repeat that ends the run marks both cells and the member `path` (`spot-duplicate-locker`). Probe exactly what the solution looks up: `any(k in seen for k in keys)` stops at the first hit, so the keys after it are not probed (`valid-sudoku`).
- **A loop over a set** draws the set in its loop order (`list(seats)`), fading the members already visited, and probes what each step asks (`probe(seat - 1, label="seat - 1")`, then each seat a walk counts up through, ending on the miss). A run of consecutive values found that way is a span on an `array` of the same values sorted, one span per run (`len 3`), with the longest a `below` span; its title ("the same seats, by number") says the solution never sorts them (`longest-seat-run`).
- **A set of composite keys** gets one `set` per key family, each member written short (`"1:5"` for row 1, digit 5; `"0,1:5"` for box (0, 1)), with the family named in the view title. Each key moves in from the cell that made it, a grid address `[row, col]`, with `value=` the key, since the cell's own text is only the digit (`valid-sudoku`).
- **Strings** longer than about 4 characters go in table cells: `array` cells are a fixed 46px. A table cell is a move's address, `[row, col]`, so a word still moves out of its row (`group-anagrams`). A string walked letter by letter is an `array` of its characters; a string that grows is an `array` padded with `""` to its final length, so cells keep their place, each written character moving in from the table cell it came from, with the length's digits from its length cell (`chat-log-codec`).
- **Intervals** sit on one number line, an `intervals` view, never two tables: the input sorted and the output so far are two `groups` over one axis (pin it with `domain` in the run `setup`, so it holds still while the output grows). Light the interval read, mark the output interval it lands in `good`, and move it there: `moves=[move(at("line", [0, i]), at("line", [1, j]))]`, an address being `[group, index]`. The boundary compared is a `points` entry on the axis (`{"at": last_end, "label": ..., "mark": "lit"}`), drawn from its value before the step, not in `vars`. The last frame marks the output group `path` (`merge-reservation-slots`).
- **A queue** (a BFS frontier) is a `queue` view, never a list in `vars`: a horizontal pipe, front on the left, with each value tagged by its BFS layer (`[i, {"en": "min 2", "ko": "2분"}]`), the same tag its cell carries on the grid, so the queue shows one wave followed by the next. A grid cell's address is `[row, col]` and a queue's is the position from the front. A value joining moves in from its cell, `move(at("tray", [r, c]), at("queue", back + i), value=f"{r},{c}")` (pass `value`: a cell carries its glyph otherwise), marked `good` in the queue. The front leaving is its own frame: it stays at position 0 marked `lit` and moves out to each cell it changes, `move(at("queue", 0), at("tray", [nr, nc]))`, or is dropped (`move(at("queue", 0))`) when it changes nothing; what it changed joins the back on the next frame. The minute is the layer tag, not a `vars` value; the last frame marks the cells of the last minute `path`, so the answer reads off their tags, and dims what is still queued when the loop stopped early (`rotting-donuts`). A deque (a sliding window's monotonic deque) is the same view with `"deque": True` in its config, open at both ends.
- **A swap on a grid** (an in-place transpose, a row reversed) is two moves between cells on the frame that makes it, one pixel each way: `moves=swap("image", [i, j], [j, i], a, b)` with `a` and `b` the pixels there before the swap (a move carries what its cell draws after the step, which is the other one). A row reversed is one frame with a swap per pair, the middle cell of an odd row none: light the row and mark the swapped cells `good`. The phase and a step count are the caption's, not `vars` (`rotate-pixel-art`).
- **A graph relaxation** (Bellman-Ford, Dijkstra) keeps the costs in arrays indexed by node, never a `table`: for a round-limited Bellman-Ford, `last` (what every edge reads) and `now` (what this round writes). A graph address is a node id or an edge `[from, to]` (either order on an undirected graph). The edge tried is one frame with two moves: last round's cost goes up onto the edge, `move(at("last", a), at("cafes", [a, b]))`, and the sum comes down into the cost it beats, `move(at("cafes", [a, b]), at("now", b), value=cost)`, marked `good` there; a sum that doesn't beat it is dropped at the edge, `move(at("cafes", [a, b]), value=cost)`. A round's start moves each reached cost up from `now` into `last`. An edge from a node not reached last round has nothing to move: light the edge and say why in the caption. The last frame marks the route's nodes and edges `path`, and in `last` the costs it used (`cheapest-courier-route`).
- **Bit tricks** are an `array` with fixed-width binary tags; the running value is an `output` box of one chip, decimal and bits, that each value moves into (`lonely-candy`).
- **Pointers over one array** are carets, and each region they bound is a span: the kept front (`dedupe-textbook-shelf`), the settled 0s, 1s and 2s (`sort-colors`). A copy is a move between cells, `move(at("books", i), at("books", k))`; a swap is `swap(view, i, j, a, b)`, the two moves with the values before it (`sort-colors`, `missing-sock-number`). A reverse is a move per cell to its mirror place, the middle one of an odd range staying (`next-speaker-order`, whose falling tail is a span and whose pivot a `below` span while the search for its swap partner runs). `WalkthroughsMatchSamplesTest` fails on an array cell that changes with no move into it.
- **A running product or count** is a span over the cells it covers, labelled with its value, moving from the span's nearest cell into the cell it fills (`product-of-all-other-elements`); a candidate with a count is a `map` with `slots=1` that each vote moves into as `+1` or `−1`, struck when the count reaches 0 (`majority-boss-vote`).
- **A table wider than about 7 data columns** is clipped at 390px: turn it, one row per item (a 9-wide table becomes 9 rows of k columns).
- **A window** is a span on its array, never `vars` values: `"spans": {"window": span(left, right, {"en": f"window {length}", "ko": f"구간 {length}"}, fade=True)}` draws a bracket above the cells labelled with its length and fades the cells outside it; the `left`/`right` pointers stay as carets, and cells not read yet are `unread` (dashed). The best so far is a second span, `span(a, b, {"en": f"best = {best}", "ko": f"best (최장 길이) = {best}"}, below=True)`, dashed under the cells, marked `good` on the frame that beats it. The counts in the window are a `map` with `slots=k` when the window holds at most k keys, so the key that overflows shows red; that frame marks the window span `bad`. Each element dropped from the left is its own frame: it moves out of the map back to its cell (`move(at("window", g), at("queue", i), mark="bad")`), and a key whose count reaches 0 stays with value 0 and in `struck` for that frame. The last frame hides the window span and the pointers, marks the best span and its cells `path`, and the caption says where the run actually ended when the best window came earlier (`unique-genre-window`; the public skill's `examples/window-at-most-k-distinct`).
- **A running value** with a place (a prefix sum, a window length per right end) goes `under` its cell: `"under": [[i, str(total)]]`; a count of each running value is a `map` the reading moves into (`battery-window-tally`).

## Marks, tags and ids

- `lit` wins over `good` on the same item: mark a changed cell `good` only.
- A `vars` item's `mark` colours a number; the chips of a list value ignore it.
- For an index-slot or cyclic-placement problem, tag each cell with what it stands for (`for 3` / `3번 칸`), and draw each placement as a move between cells: a swap into place is two (`missing-sock-number`), and a slot marked for the value read is a move from the cell read into the slot, or a move with no `from` when a cell marks its own slot (`repeat-attendance-codes`). For a running count, tag each read cell with its effect (`+1`, `−1`). Tags take Text (`missing-sock-number`, `majority-boss-vote`).
- A view id `answer` or `moves` collides with `run.frame(answer=..., moves=...)` (a TypeError): name it `result`, titled "answer".
- View titles are uppercased by the kit's CSS; a table with no `columns` draws no header row.
